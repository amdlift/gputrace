# Close the `dlopen` escape by interposing `dlsym`

ADR-0003 closed two resolution paths and claimed no call path escaped capture. A third does: `dlsym` on a handle from `dlopen("libcuda.so.1")` searches that object alone, so `LD_PRELOAD` has nothing to shadow and the dispatch-table hook is never asked. This is not hypothetical and not a corner — measuring real stacks (`docs/dlopen-escape.md`) found it is how the CUDA Runtime reaches the driver (it `dlsym`s `cuGetProcAddress_v2` off the handle and resolves everything through the driver's own dispatch table), how cuBLASLt reaches it (32 entry points taken off the handle at load, `cuLaunchKernel` among them), and that a stock `cudaMalloc`/`cudaMemcpy` program under `gputrace capture` produces **no bundle at all** while doing real work on the GPU. An ollama inference run, 100% on GPU, recorded three device-query calls and not one launch.

We will **export our own `dlsym` (and `dlvsym`) and answer `cu*` lookups with our trampolines**, leaving every other name a pass-through. One hook covers both mechanisms: the Runtime's lookup of `cuGetProcAddress_v2` comes back as our dispatch hook, which ADR-0003's machinery already handles, and a direct lookup of `cuLaunchKernel` comes back as the shim. The work is #15; this ADR records the decision, not the implementation. Two constraints come with it. The hook sits on every library's startup path, so it must be a cheap prefix test and then a tail call into the real `dlsym` — and it must *not* touch the record path, which keeps ADR-0004 intact, because all of this is resolution-time. And our own resolver (`real.rs`) calls `dlsym`, so the hook would re-enter itself; the guard has to be a thread-local flag around our resolution, not a comparison against our own driver handle, since `dlopen` of one path hands the target and us the same refcounted handle.

The alternative we keep in reserve is `LD_AUDIT`: `la_objsearch` can redirect the target's search for `libcuda.so.1` to our object, so the handle it gets *is* us and no `dlsym` hook is needed. It is cleaner in principle and worse in practice — a second loading mechanism and a second environment variable, process-wide and unforgiving — so it is the fallback if interposing `dlsym` proves unstable, not the first move. Doing nothing was rejected: the stacks that escape are the stacks the project exists to capture, and leaving the claim as it stands would put a false coverage statement in front of evaluators.
